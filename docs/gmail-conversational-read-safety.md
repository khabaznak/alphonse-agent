# Gmail conversational reads: integration safety

Status: incomplete; the native Gmail unread-count definition is intentionally **not registered**. `GmailUnreadService` and its account-choice proof are synthetic-testable foundations, not an authorized production path. Account connection or an actor identity does not establish a confidential answer destination.

## Enforced in the isolated foundation

- A one-off count uses a currently authorized actor, Google connection, `mail_read` scope and a grant covering the requested label or explicit mailbox-wide resource. The adapter rechecks grant revision and cancellation around provider I/O. The result contains only provider-reported count, label, unit and observation time, and is withheld when an injected private-delivery verifier changes during I/O.
- Multiple accounts cannot be selected by a model-provided connection ID alone. The server-issued choice helper records a challenge tied to actor, task, origin, label, unit and the exact current account choices. Only an authenticated single-choice answer to that server-issued question can select among those choices; later challenges supersede earlier ones. Current grants and scope must be checked again at use. The helper assumes the caller has already fenced both question delivery and final response; it is not connected to the running runtime.
- Tool-call UI events and V2/V3 tactical UI projections are actor scoped. Unknown actors do not broadcast sensitive task/tool/question events. Task owner takes precedence over a delegated respondent when an event contains the full owner's task. This is a general UI privacy improvement; it does not protect all downstream surfaces.

## Required before registration

1. **Trusted destination evidence.** Inbound `CommunicationChannel.queue_message` accepts metadata with an existing `channel` and uses `setdefault`; a raw task metadata field is therefore not proof of a private destination. Bind an authenticated, server-sourced channel identity and confidentiality classification to the task. Prove the destination belongs to the actor; deny group or unknown audiences. Recheck at delivery and after continuation/restart, including Desktop user switches, Telegram group/supergroup and Discord guild/thread paths. Do not infer privacy from provider name or an inbound `is_private` claim supplied as generic task metadata.
2. **Durable source taint and recipient fencing.** Persist a task-scoped, actor- and source-bound confidentiality label before a provider count or private account choice can enter model-visible state. Every subsequently generated action, plan, message, attachment, shell/program call, memory write and scheduled follow-up must respect it, including runs resumed from checkpoints and user steering. Apply an independent deterministic audience check to `native.deliver_message`, attachment/message sends, outbox projection, direct response, notification mirroring, and any external or user-shared output. Explicitly authorized disclosures require a separate auditable authorization boundary; a semantic model verdict or a generic project membership is insufficient.
3. **Controlled question issuance and delivery.** The server—not a model-authored generic question—must issue the challenge from a freshly authorized list, deliver it only through the private channel boundary, park and resume the correct task, and consume the authenticated respondent's answer. Reauthorize the complete candidate set and selected grant immediately before the provider call. Expired, stale, superseded, replayed, altered, wrong-actor, changed-origin and revoked choices fail closed. A generic user-facing question is not authority to choose a mailbox.
4. **Evidence, memory and event isolation.** `ToolInvocationService` records result data in memory; the V3 executor records it in task action/evidence and checkpoints. Determine and enforce the visibility, retention, redaction, export and deletion behavior for all copies, summaries, knowledge extraction, UI surfaces, diagnostics and logs. Verify private source data cannot flow to a shared project ledger or another household member. UI ownership scoping is not a substitute for data-flow controls.
5. **Action and effect fencing.** Make cancellation, actor and grant revocation, scope and delivery authorization effective at every read and output boundary. Prevent model-composed Bash/programs or alternate tools from forwarding private state around the fence. Ensure privacy taint survives a crash between provider read, task checkpoint and response, and a failure cannot downgrade or discard it.
6. **Synthetic end-to-end qualification.** Exercise complete real processor, question, daemon/IPC and outbox paths with disposable provider/grant fixtures. Include two users, Desktop polling and user switches, Telegram/Discord groups, private channels, delegated users, model attempts to forward or reclassify data, model-invented account IDs, revoked grants, wrong/expired/superseded answers, restart, cancellation and result/telemetry/history inspection. No real mailbox access, credentials or private identifiers are needed. A fake injected privacy callback or a single unit test does not qualify this boundary.

Only after these controls have been implemented, independently reviewed and passed end-to-end should native registration and live/manual qualification be considered. The current issue does not authorize a real-account test or provide a privacy boundary by itself.

## Existing-storage boundary and next vertical slice

Use the existing task checkpoint as the durable source of truth for any future private-data label; do not add a separate script or taint registry. The normal persisted installation places the question/checkpoint and outbox stores in the same SQLite database, but injected stores and `:memory:` tests may be separate. Enforce same-database identity explicitly before assuming an atomic relationship.

Current V3 `SQLiteQuestionStore._save_task_checkpoint` uses `INSERT OR REPLACE` without a general version fence. A label placed only in `task.metadata` can therefore be lost by a stale writer. The experimental single-loop checkpoint uses version-fenced updates to the existing task row, but is not the production runtime and its writer protects only its own stamped engine. Do not infer the same safety for existing V3 or migrate active V3 checkpoints into that engine.

`V2Daemon.run_once` can project a completed response in a transaction shared by outbox, conversation and schedule only if their file-backed database paths match; terminal checkpoint marking happens afterward. Question and communication delivery can also enqueue through their own paths. The generic tool boundary can invoke Bash, programs, delivery and other tools, and `ToolInvocationService` records results in memory. `LedgerMemory._scope_dir` may use a project-root ledger shared by project members. These paths mean a private-channel test at Gmail read time, an audience ID on an outbox row, or actor-scoped UI events does not contain derived private content.

The next minimal, synthetic-only slice should use the **existing experimental task row** and its CAS transaction to persist an immutable actor-bound private-data label before a fixture read can return private evidence. Until a separately verified destination and complete information-flow policy exist, deny every subsequent egress-capable tool or program, generic memory/knowledge write, question or communication delivery, outbox projection and automatic mirror. A locally prepared response may be retained privately but must not be projected. If an action cannot prove both actor identity and the same authoritative durable task state, it fails closed; this includes database mismatch, missing or malformed label, stale checkpoint and uncertain dispatch. The slice is not permission to activate Gmail.

Its integration tests must use disposable fixtures and the real checkpoint, tool invocation, memory and outbox boundaries. Verify: pre-read durable marking; crash/restart and a stale writer cannot remove the marker; wrong actor and swapped task cannot use it; distinct database paths fail closed; Bash/program, recipient delivery, question delivery, attachment, mirror and final outbox are denied; no private content enters shared project memory, other-user UI or telemetry; and an interrupted/unknown read cannot be retried or silently downgraded. Include an unaffected non-private task to prevent changing ordinary behavior. Review all alternate paths and race windows before expanding the allowlist or claiming protection.

## Candidate: direct read-to-private response

A narrower alternative to task-wide taint is possible only when the result does **not** enter the generic agent task at all. This is a design proposal, not a supported or implemented path:

1. A trusted ingress associates an explicit user request with the authenticated household actor and a verified, actor-private response destination. A bounded Jev judgment may identify the requested capability; deterministic code validates actor, request freshness and whether the one-off read is authorized. When the meaning is uncertain, ask or report the unsupported route; do not treat a model-generated account ID as user selection.
2. A server-owned Gmail read operation checks the actor, current account/grant/label and read-only scope. If multiple accounts match, it issues a server-authored, actor- and request-bound choice through the same verified private destination, then checks the stored answer and all current grants. `gmail_choice.py` is a foundation only: its task-metadata origin and choice-delivery preconditions are not yet trusted proof.
3. The server formats a bounded response itself and sends it directly to that verified destination. Neither the count, account choices, nor a reversible secret-bearing handle is returned to System Two, placed in its tool results, sent through generic memory, written into a project-shared ledger, or broadcast through UI/activity/telemetry. A future history record must be actor-scoped with explicit retention and never become shared context merely because a project is active. The generic task may receive only a non-sensitive status that does not enable accidental duplication or claim a delivery it has not verified.
4. Response enqueue and an idempotent delivery receipt must be committed together against the same durable request identity; cancellation and grant/audience revocation must be fenced at each meaningful read and delivery boundary. On crash, retry reconciles a previously claimed or uncertain send and never re-fetches or re-sends blindly. No second mailbox read is used merely to recreate a missing response.

### Current blockers to that route

- `CommunicationChannel.queue_message` accepts caller-supplied channel metadata, so a task's origin fields are not server-attested private-destination evidence. Telegram and Discord can originate in group channels; `audience_user_id` on an outbox row does not make the target private. The question-delivery resolver may choose a different channel from the origin and needs a separately verified recipient/destination at delivery time.
- The local optional-management IPC uses an owner-only Unix socket and kernel OS-peer identity, which authenticates the **local OS principal**, not a particular household member, Desktop window or conversation. The generic Desktop IPC can relay requests; no request-bound private Desktop delivery receipt links an assistant decision to one verified UI recipient. It is therefore not sufficient to expose a new count endpoint and assume only the intended chat can invoke or receive it.
- Native Bash is deliberately trusted host execution, not a filesystem or process sandbox. A same-OS-user subprocess can use local interfaces and files within its host authority. A direct response architecture can keep data out of normal model tool results, but it cannot honestly promise confidentiality against arbitrary same-user Bash execution merely by hiding an endpoint or token. Any stronger boundary needs an explicit OS/process isolation or capability design; do not silently redefine Bash as sandboxed.
- Existing tool invocation emits model-visible results, task evidence, UI events and memory events; routing the count through `native.gmail_unread_count` first would already defeat the bypass. Existing completion and outbox mechanisms expect the agent to prepare response content, and their normal fallback/retry logic does not yet provide the direct path's receipt and no-duplicate guarantee.
- The choice issuance helper parks via the generic question store, but delivery and resumption are not integrated with a verified private audience or a direct-read request. Returning a list of account labels through the ordinary tool result would itself expose private account metadata before selection.

A safe, measurable vertical slice would use a synthetic, non-network Gmail provider and an injected destination verifier backed by a **server-owned test channel record**, not model-supplied task metadata. Exercise the real ingress, question store, account authorization, bounded read, formatter and durable outbox/delivery receipt together; inspect all tool events, task checkpoints, memory/knowledge, conversation history, UI streams and provider telemetry. Include actor switching, forged `channel` metadata, wrong/superseded choice answers, grant revocation during I/O, cancellation, group or unknown channels, changed destinations, restart between enqueue and delivery, and no duplicate sends. The test must demonstrate that neither a hidden generic-tool result nor a test-only callback is mistaken for a production trust boundary. A production path additionally needs a reasoned treatment of the trusted host/Bash limitation above. Until those prerequisites exist, keep #211 unregistered.
