Architecture proposal · for evaluation

One loop, with safeguards at the edges

Replace the separate strategic-phase and tactical-action loops with one durable task loop. Let code enforce the rules; ask Jev only questions that require semantic judgment; use System Two for planning, tool calls and language.

Proposed flow

The same loop handles a simple question or a multi-step task. Dashed Jev box = conditional; solid nodes = runtime flow.

Safeguards that stay

Before a call

  • Actor-scoped account and data access, skill bindings, revocation, prerequisites and mutation scope.
  • Cancellation, steering and task-wide resource budgets, checked at action boundaries.
  • Jev relevance is advisory and cannot authorize access or hide an authorized capability permanently.

After a call

  • Persist results and provenance. Verify requested effects with operation-specific receipts or independent read-backs where required.
  • Do not repeat a mutation whose effect is uncertain; reconcile first.
  • Failed, partial or missing evidence cannot become success. Bound semantic uncertainty and return an honest unknown or blocker.

Across interruptions

Checkpoint the task, outstanding question, evidence, remaining budgets and uncertain effects. Resume with the same actor and scope; prevent duplicate effects. Preserve existing lifecycle, privacy, authorization and terminal-state invariants during any migration.

How the Gmail question would flow

1. Identify that the user asks about current Gmail access and an unread count. Check the requester’s current connection and grant state.

2. If an authorized, supported count capability exists, invoke it within scope and use its result. If not, explain the actual missing capability or permission.

3. Answer in Spanish with the verified count, or say the count is unavailable. Do not search old conversations to infer current access.

This is proposed behavior. The current Gmail adapter is wired to source acquisition; a conversational count capability and its exact coverage would need implementation and tests.

Prove it before replacing V3

Compare on the same tasks

Replay synthetic everyday reads, multi-step tasks, failed tools, missing information, interrupted writes, changed forms and permission denials. Include held-out cases and independent effect checks.

Measure outcomes and cost

Measure verified completion, honest unknowns, unintended effects, unnecessary questions, repeated calls, input/output tokens, latency and cost. Set and enforce budgets from measured baselines.

Roll out behind a switch

Keep the current engine as a rollback path. Start with read-only conversational tasks, then evaluate higher-risk mutations and restart behavior before expanding. This design is a hypothesis, not a demonstrated improvement.
