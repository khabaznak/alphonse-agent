# Dojo: activity and recovery experience

This exercise concerns the experience of a person waiting for a multi-step request and then encountering a failure. It supplements the conversation failure diagnosis exercise; it does not grade a model by counting tool calls. The disposable conversation contains an older tentative picnic location, a later plan, and an unconfirmed prerequisite, followed by unrelated turns. The owner asks for the latest plan and remaining uncertainty. Alphonse may choose any authorized route or honestly report that he cannot determine the answer. No expected wording or tool sequence is given to him.

The evaluator injects a provider fault after two model-selected tool actions, pausing immediately beforehand to request the actual owner-worker activity over IPC. The event count reflects recorded observations, not necessarily the number of selected actions. It then records the terminal status, activity and available recovery items. If two actions are not selected, the fault is **not triggered**; preserve that attempt rather than silently retrying or treating it as a failure of the UX. The exercise makes no real household changes. Run with a fresh journal and an authorized configured model:

```sh
.venv/bin/python -m alphonse.agent_v2.evaluation.dojo_activity_ux /tmp/dojo-activity-ux.json --model MODEL
```

The receipt contains provider-reported usage when supplied, elapsed time, returned decisions and any error or injected interruption. Report actual monetary cost if known, otherwise unknown; do not infer cost from elapsed time. Provider inference may run outside the disposable host. Scripted providers verify the harness only. IPC is the product worker path, but the runner does not render Desktop, exercise a recovery action, verify a real household outcome, establish accessibility, or demonstrate that a person understood the experience. An infrastructure error and an early answer must be kept as such. One run cannot establish general reliability or multilingual behavior.

## Critic's independent review

A pragmatic UX Critic should inspect the actual rendered Desktop during the live and failed states, the user's request, the IPC receipt, and evidence of any recovery action actually taken. Compare the UI to independently observed events; do not infer hidden work from a progress message. Record **pass, fail, or unknown**, evidence and a concise reason for each item. A missing state or unavailable rendering is unknown, not pass. Record the Critic's overall verdict separately from the IPC receipt; a fixture, successful test, or plausible string alone is not the verdict. Iterate on failed items, retain prior results, and ask the Critic to review again. Do not mark overall pass until the Critic has assessed the relevant rendered states and recovery path.

Alongside each verdict, record a UX score from **0 to 10** when the observed evidence supports one: **0** means among the worst imaginable implementations or severe UX problems, **5** means mixed or merely serviceable with material shortcomings, and **10** means masterful execution. Intermediate scores express the Critic's reasoned judgment, not a statistical measure. State the exact scenario and evidence supporting each score. If a criterion or important part of it was not observed, mark that scope **unknown** instead of estimating it; a score for a narrow fixture must not be presented as a score for the product. An overall score is appropriate only for a clearly identified scope with enough evidence; otherwise record it as unknown. Do not average away serious failures or treat any score as an automatic pass: pass/fail/unknown and outstanding risks remain independently stated. Preserve earlier iterations and scores when revising a review.

1. **Comprehension and relevance:** Can a person tell what Alphonse is doing for their request and what materially happened? Are repeated routine events grouped or otherwise readable, with technical details secondary rather than a wall of exit codes?
2. **Honesty and uncertainty:** Do live, stopped and failed states match observed evidence? Are unknown effects and incomplete observations clear without suggesting that every successful read had an unconfirmed side effect? Is there no unsupported success, cause, or invented intent?
3. **Recovery:** After failure, can the person identify a relevant available next action, and does it actually perform the stated action on the correct request? If none is available, is that clear without implying a nonexistent control? Inspect action behavior, not just a label; avoid exposing private details.
4. **Continuity and attention:** Is the association with the original request clear, without competing duplicate progress indicators? Check changes as work starts, progresses, stops, reloads or loses connection; where not exercised, record unknown.
5. **Accessibility and inclusion:** Can status and controls be perceived, navigated and understood, including keyboard and assistive-technology checks where available? Review natural language and representative languages without requiring specific phrases; untested modes remain unknown.

Use the five Dojo pillars as interpretive lenses: resourcefulness and resilience require evidence of the agent's behavior, accountability and trustworthiness require comparing user-facing claims to recorded effects, and human understanding requires inspecting the actual interaction. This exercise focuses on visibility and recovery; it does not by itself establish a general score for any pillar. Record which are not assessed.

A [scripted-provider receipt](dojo-activity-ux-scripted-receipt.json) records one triggered attempt and one early-answer attempt. The former records two observations followed by the injected failure; the latter does not trigger the fault. Both used simulated token counts, cost no model API spend, and leave the Critic verdict unassessed. The receipt is worker/IPC evidence, not a rendered UX review.
