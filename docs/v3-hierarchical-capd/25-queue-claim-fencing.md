# Queue claim fencing foundation

Status: default-off experimental queue slice for #216. The normal runtime still uses message ID and lease owner for its claims and acknowledgements. Only an explicit `SQLiteMessageQueue(..., experimental_claim_fencing=True)` construction installs the additive generation column and issues internal receipts. Existing runtime settings and constructors do not opt in. No production readiness claim follows from the standalone tests below.

## Existing gap

`SQLiteMessageQueue.claim_next` claims a row by setting processing status, owner and expiry. `ack`, retry and several handoffs use the message ID and owner. A stale worker can therefore resemble a later worker when the owner is reused. `attempt_count` is not an ownership generation: scheduled handoff can decrement it, and deleting/re-enqueuing a message can reset it. Ownership must also account for lease expiry and the authenticated queue user.

## Unwired contract

`core/messages/claim_fence.py` provides an internal `ClaimReceipt(message_id, user_id, lease_owner, claim_generation)` and a fresh opaque 128-bit token from `new_claim_generation()`. The token identifies one acquisition, not authorization or an effect receipt. It must never be logged or included in model/user content. The user ID is the actual queue message's user; a task resumed by an authenticated respondent may have a different task owner, which must be checked separately by the existing question/delegation rules.

`fenced_claim_transaction(conn, receipt, clock=...)` uses `BEGIN IMMEDIATE` and checks the same row's message/user/owner/generation, processing status and live expiry before and immediately before committing SQLite writes. The caller may only change other tables within that transaction and must not commit or roll back it, modify the claim row, perform external I/O or write another store. A lost/expired claim or backwards/invalid clock rolls back; missing generation schema fails closed. The clock is injected and must return an aware datetime; the stored expiry must also be parseable and timezone-aware.

This is not a claim-acquisition, renewal, acknowledgement, release, retry or handoff API. It does not fence provider calls, already-dispatched effects, memory stores in another database, UI events, or an outbox provider's later delivery. A trusted Python caller can still manually commit or otherwise violate the transaction contract; the helper cannot undo that. Any consumer must make its DB writes and final claim check in the same transaction and separately establish actor authorization, cancellation and effect safeguards.

## Requirements before use in the runtime

1. Migrate the production queue schema safely and atomically. Each successful claim—including a reclaim or same-owner reacquisition—must store a fresh generation together with processing owner and expiry, in the same transaction. Re-enqueue with a reused message ID must never restore the prior generation. Do not infer ownership from `attempt_count` or lease owner. The random nonce supplies an unguessable, effectively unique generation; a collision or missing/invalid token must fail closed, not reuse the old claim.
2. Establish upgrade, downgrade and crash semantics for rows claimed by older code. In-flight legacy workers without a generation must be drained or safely reconciled before generation-fenced processing; do not silently adopt them as fresh. Mixed-version writers that bypass the token must not be able to claim, acknowledge or mutate a generation-fenced task. Test migration/rollback on disposable databases without deleting queued or in-flight work.

The migration's immediate transaction and one-time check do not establish that drain: an older process can claim a pending row after the transaction or delete a new claim using the same lease owner. `tests/test_queue_migration_compatibility_diagnostics.py` reproduces both with disposable legacy-style SQL; these passing diagnostics demonstrate a blocker, not compatibility. A persistent trigger-based compatibility gate would have to cover every writer while preserving enqueue, user deletion, recovery, downgrade and crash semantics; it cannot revoke external effects already dispatched. Do not install such a gate or activate fencing until the complete lifecycle and a verified old-worker drain are implemented and tested.
3. Carry the receipt internally from claim to every task boundary. Atomically fence checkpoint updates, supersession disposition, owner-scoped memory writes and outbox enqueue where supported. Check the current task/checkpoint version as well as queue ownership. For authenticated answers, preserve the actual queue respondent and verify the existing task/respondent relationship; never assume the queue user and task owner are identical.
4. Implement separately reviewed, generation-fenced ack, retry, cancellation, lease renewal, scheduled handoff and release operations. Their own terminal mutation of the claim row cannot run inside the present helper because its end check deliberately rejects claim-row changes. A stale worker must not acknowledge or release a newer claim, including when the owner string is reused or an attempt counter is reset.
5. Define explicit stale/superseded control flow for CoreLoop and daemon: no stale terminal response, memory finalization or notification; no accidental acknowledgement, retry of an uncertain effect or duplicate delivery; preserve the newer checkpoint and its queue claim. A task may need a safe reconciliation or user-visible blocker, depending on what already happened. `ProcessingStatus.YIELDED` alone is not a complete ownership protocol.
6. Before and after any external I/O, recheck cancellation and current actor/resource authority. Reconcile possible writes or deliveries before retry; a queue token cannot authorize access or make an external effect atomic. An outbox enqueue fenced in SQLite must still validate current recipient/channel authorization at dispatch.

## Evidence

`tests/test_claim_fence_foundation.py` uses the real queue table in a disposable SQLite file and adds the proposed generation column **only to that temporary database**. It covers same-owner token rotation, reinsert/ABA, owner/user/status changes, expiry, backwards time, rollback on claim-row change, competing SQLite writers, a missing legacy column and token redaction. It does not prove real queue migration, production claim issuance, cross-store consistency, authenticated question resumption or provider-delivery behavior.

## Default-off queue slice

The opt-in queue refuses activation when any legacy processing row lacks a generation. Its claim transaction assigns a fresh nonce, refuses reuse of the current row's nonce and returns a receipt only on the internal `QueuedMessage` object. Fenced acknowledgment and an already-staged handoff release verify actor, message, owner, generation, status and expiry in a locked transaction, recheck time after mutation, and roll back if the lease expires or the clock moves backward. This new binary's legacy claim, ack, retry, cancel, event-finish, handoff and reclaim paths do not mutate generation-bearing rows. Queue acquisition and reclaim exclude supersession holds when the opt-in hold table exists.

Fenced mode currently rejects event-automation acquisition: event receipt rows do not retain a claim generation after inbound-row deletion. Receipt-aware handoff staging, delivery waiting, retry, cancellation, renewal, durable supersession disposition and recovery are not implemented; unsupported paths fail closed. The existing daemon and CoreLoop do not propagate or use receipts, lease heartbeats are absent, and pre-migration binaries can still bypass the new column. Do not turn on the experimental constructor in household runtime or infer mixed-version safety from the tests. The proposed hold triggers also interfere with the current multi-transaction household-user deletion flow; a separately reviewed actor-scoped durable deletion gate and privacy-safe recovery are required before installing them in a live household.

The opt-in queue now exposes a one-shot `renew_claim_fenced` operation. It requires the exact receipt, a nonblocking caller-supplied task-cancellation check, and a bounded lease duration; it preserves the generation, serializes with SQLite reclaim, and rolls back if cancellation occurs, the original lease expires during the update, the clock moves backwards, or a hold is present. This operation starts no heartbeat. The cancellation callback must be bound to the real task and must not block on the held database lock; a stale callback or a kill switch changing immediately after the final check cannot be excluded by this local helper. CoreLoop/daemon scheduling, lifecycle cleanup, durable holds and cross-process version barriers remain necessary before activation. The migration also rejects nullable/lookalike generation columns and malformed existing generation values rather than adopting them.
