# Superseded checkpoint: runtime integration design

Status: design only for #216. The production queue and agent do not enable supersession handling. Experimental primitives include read-only inspection, claim fencing and an explicitly installed hold; they do not acknowledge, resume or resolve work.

## Required safety outcome

A worker that loses its actor-bound checkpoint or queue claim must not finish memory, publish a stale result, acknowledge another worker's message, retry an unconfirmed effect, or delete the only durable continuation. Cancellation and other actors' inputs remain authoritative. A claim generation is a lease identity, not permission or proof of an effect.

## Concrete integration points

1. `SQLiteMessageQueue.claim_next` must atomically issue a unique claim generation with the real lease owner and expiry and return it in the actual `QueuedMessage` from `dequeue`. An opaque, internal `ClaimReceipt` carries message ID, authenticated queue user, owner and generation; do not put the token in task state, telemetry, model prompts, UI or logs. Failed acquisition must not return a receipt. In-memory and different-database paths must provide equivalent fenced semantics or explicitly refuse the new path.
2. The exact receipt and actual dequeued message must travel through `AlphonseCore.step` into an internal processing context and back in `LoopStepResult`. `V2Daemon.run_once` currently calls `peek` before `step`, so the peeked item must not be used to attribute a superseded message or its notification. The processor's checkpoint CAS must bind the task owner, task ID, engine/schema and expected checkpoint version independently of the queue respondent; a cross-user answer requires the existing authenticated question-to-task relationship.
3. The processor needs an explicit, sanitized `SUPERSEDED` outcome when a checkpoint CAS loses. Unlike ordinary `FAILED`, it must not call failure explanation, finish memory, acknowledge consumed steering, publish a terminal `run_finished` or use a stale snapshot as the visible state. It must not use `YIELDED`: that path in `daemon.run_once` assumes a scheduled handoff and calls its release/cancel operations. Existing processors must not emit the new outcome until the downstream queue contract is implemented.
4. `AlphonseCore.step` and `V2Daemon.run_once` must carry that outcome without replacing visible state from the stale task, publishing task completion, projecting outbox/notification, marking a checkpoint terminal or acknowledging/retrying another claim. UI/activity events are emitted during execution today; a final-result check cannot retract an event already observed. A future implementation must establish a safe publication boundary for each event (or buffer bounded events until the current claim and authority are checked), as well as fence any durable memory work that occurs before finalization. Event filtering by user alone is not a claim fence.
5. Add a queue-owned atomic `park_superseded` transaction against the exact live claim, owner and generation and current checkpoint. It must preserve the checkpoint/evidence and stop all automatic reclaim or retry until a separately authorized recovery decision exists. Current `v2_inbound_messages.status` cannot represent a durable hold; `retry_wait` with an artificial far-future time is not an acceptable implicit quarantine. A reviewed schema migration or equivalent durable hold table must be reflected in every claim/reclaim/ack/retry/scheduled-handoff path and operational recovery UI. If the claim expired, was reacquired, has unknown ownership, uses a different DB, or cannot be parked atomically, fail closed and require recovery; never acknowledge a newer claim.
6. Recovery must distinguish cancelled, waiting-user, queued/running newer, terminal, missing/mismatched task, and uncertain external effects. Do not acknowledge waiting work until its question and continuation are durably established; do not enqueue a second continuation unless a single idempotent owner-bound driver is guaranteed. Cancelled or uncertain external writes require effect/receipt reconciliation before any retry, not automatic replay. A resumed task reloads its latest checkpoint and rechecks current actor/resource authorization, revocation, cancellation, budgets and engine stamp.
7. Generation fencing must cover the existing `ack`, `retry`, `requeue`, `reclaim_expired`, `stage_scheduled_handoff`, `stage_delivery_wait`, `release_scheduled_handoff`, `cancel_scheduled_handoff`, and manual/recovery paths, as applicable. Leases currently default to 60 seconds with no general heartbeat; prevent a live worker from continuing after expiry and define recovery rather than making liveness assumptions.

### Publication boundary before a superseded outcome

Do not add or enable a processor/core/daemon superseded outcome until the exact claim can be atomically held and all publications are fenced. `AlphonseCore.step` starts memory and invokes its active-task callback before the processor returns. Its context forwards UI and delivery sinks to tool execution directly: question, message and attachment tools can publish or create durable deliveries during processing, as can the V3 processor. Activity events and daemon presence/event-processing updates also happen before the final status. A new return status cannot retract these effects.

Buffering only the final snapshot or checking the lease immediately before flushing an in-memory UI buffer leaves a race between the check and publication. A candidate design must stage each private publication, including tool-originated events and durable outbox work, in the same database transaction as an exact live claim and applicable actor/checkpoint/cancellation checks. A separate dispatch protocol must define claim or publication ownership, revocation, crash/restart and uncertain delivery semantics; user-facing events already delivered cannot be retracted. Memory, event lifecycle, presence and activity must either use equivalent fencing or remain unavailable on this path. Bound any buffer and fail closed on overflow; never silently drop evidence or task output. Different-database, in-memory and unavailable-store paths must refuse the experimental execution before side effects.

`SQLiteOutboundStore.enqueue` and `project_snapshot_to_outbox` already accept an existing SQLite connection, so a same-database claim-fenced insert is feasible. Enqueue checks the supplied connection's main database path against the store and qualifies its inserts against `main`; in-memory transactions require the store's own connection. This path comparison prevents routine miswiring, but cannot prove file identity if a database is replaced or renamed while a connection stays open; future fencing also needs a stable database lifecycle or a stronger connection binding. Existing inserts immediately create `pending` rows, which the ordinary outbox consumer can claim even after the inbound claim expires or is replaced. The experimental path therefore needs a nondispatchable staging state and an atomically fenced release/dispatch protocol, including cancellation, revocation and uncertain provider outcomes; merely placing the existing insert inside a claim transaction is insufficient. Disposable tests in `tests/test_claim_fenced_outbox_diagnostics.py` demonstrate these transaction and dispatch boundaries, not a working integration.

The current outbox status constraint permits only `pending`, `claimed`, `retry_wait`, `delivered`, `failed` and `unconfirmed`. None is a safe staging state: `pending` is immediately dispatchable, while `unconfirmed` means a provider may already have received an attempted send and has existing recovery semantics. Supporting a new state requires a reviewed migration and mixed-version/downgrade gate; the current status migration detects only whether its schema text contains `unconfirmed`. It must preserve rows, indexes, triggers, idempotency and outstanding delivery state, and survive crashes without making staged rows dispatchable. Release must verify source claim generation, authenticated actor and recipient, checkpoint version and current authorization in one transaction, with idempotent operation binding; a released message still requires dispatch-time revocation and uncertain-send handling. User deletion, retention and recovery must cover staged content without partial deletion. Until those prerequisites and exact database binding are in place, the actual outbox schema and daemon path remain unchanged.

Other real sink operations require more than passing a connection: `communication.deliver` separately creates a communication thread, V3 admission writes both an outbox item and a conversation record, and question delivery can affect questions and UI events. Those records must share the same fenced transaction and authenticated task/recipient binding, or be refused before a side effect. `LedgerMemory.start_task` and `finish_task` write Markdown files and can trigger knowledge processing; SQLite fencing cannot make those file writes atomic. UI events and activity currently enter in-memory lists and may be polled concurrently. These surfaces need durable fenced publication or an explicitly safe alternative before enabling the outcome.

Integration tests must pause at barriers after staging and before dispatch while another connection cancels, supersedes, expires or reacquires the claim. Assert no stale task event, activity, notification, outbox send, memory finish, consumed-message acknowledgment or retry; test direct tool sinks as well as processor emissions, concurrent polling, overflow, crash/restart and cross-user actor binding. A synthetic status alone does not test these guarantees.

## Rollout blockers

- An additive generation column alone does not fence an older binary: old `ack`/`retry` writers can still ignore it. Mixed-version workers must be excluded by a verified drain/version gate or a database-enforced guard; do not turn the feature on merely because the new binary can generate tokens. Migration, downgrade, interrupted startup and any explicit rollback must preserve existing queued and in-flight work.
- The current claim helper only permits transactional writes to *other* rows and deliberately rejects altering the claim itself. The experimental hold inserts a separate row without altering the claim; terminal release or acknowledgment needs its own reviewed implementation and must not work around the helper's second check.
- The current `supersession_inspection` is a read-only snapshot for a narrow direct-owner case. It leaves the lease untouched and does not establish authorization, question delivery, reconciled effects, a continuation or a safe claim release. Its result is stale as soon as the transaction ends and cannot by itself authorize action.
- `context.is_cancelled` and SQLite checkpoint status can change while a provider or tool call is underway. A last-second recheck narrows but cannot eliminate that external boundary race; after uncertain effects do not repeat them without independent reconciliation. Cross-store/outbox publication cannot inherit SQLite atomicity.
- User deletion currently removes project records and files, schedules and task checkpoints before deleting inbound rows. A hold trigger then aborts the inbound deletion, leaving partial deletion and an orphaned hold. The experimental hold schema must not be installed in production until the deletion protocol below is implemented and verified.

## User deletion and hold creation

A read-only check for holds before deletion is insufficient: another worker can park a message after the check. Holding a SQLite write transaction through the entire deletion is also unsuitable: deletion opens other store connections, possibly to the same database, and removes files outside SQLite.

Before any deletion side effect, atomically acquire a durable, actor-scoped deletion gate and check that the actor has no holds in the queue database, under `BEGIN IMMEDIATE`. Every hold creation must check that gate in the same transaction that inserts the hold. If a hold wins the race, deletion must fail before touching any store or file; if the gate wins, parking must fail closed. Missing or incompatible schema, unavailable storage, or unknown actor mapping must prevent deletion when the hold feature is installed. Block delegated holds for which the queue user and affected task owner do not match until both identities are covered by the gate. The gate is not authorization: existing admin and exact-confirmation checks still apply.

The gate must survive a crash until an authorized recovery process can determine deletion progress. A complete design also needs a durable deletion journal for the already non-atomic multi-store and filesystem operation, idempotent restart, explicit treatment of uncertain effects, and a privacy-reviewed way to retire the gate after user removal without permitting a stale worker to recreate a hold or retaining identifying data indefinitely. Migration must prevent concurrent feature installation and deletion from bypassing one another; all writers and downgrade paths must honor the gate, or be drained and fenced before activation. An old binary cannot be trusted to observe an additive gate. Until those contracts exist, leave the experimental schema and park API unregistered.

Test both race orders with separate SQLite connections and deterministic barriers: a parked hold blocks deletion before the first project, filesystem, schedule, checkpoint, queue, outbox or user mutation; a committed deletion gate blocks a concurrent park and preserves the original claim and evidence. Also cover pre-existing holds, two users, malformed/missing schemas, explicit confirmation/admin failures, process crash and restart at each deletion stage, interrupted gate acquisition, migration/old-worker attempts, and safe gate retirement. A test demonstrating the race in the current implementation is diagnostic, not proof that this protocol is implemented.

## Required integration tests

Use disposable shared SQLite databases and deterministic barriers rather than timing sleeps:

- A claim expires and is reclaimed with the *same* daemon owner; the stale receipt cannot alter, acknowledge, retry, release or park the newer claim. Include delete/reinsert ABA, lease expiry during transaction, restart, renewal, and legacy/mixed-version behavior.
- Race checkpoint CAS with cancellation, new steering, an answered or parked question, a newer running/queued checkpoint, terminal status and actor/engine/schema mismatch. Verify exact checkpoint/evidence survives, no stale `memory.finish_task`, model/tool call, UI event, outbox, notification, acknowledgment or duplicate mutation follows the superseded point.
- Verify transactional hold and recovery across crashes before commit, after commit, before resume and after resume; ensure exactly one valid continuation and no acknowledgment until its prerequisite is durable. Unknown or partially dispatched effects remain held for reconciliation.
- Exercise scheduled handoff and authenticated cross-user question continuations separately; the queue claimant may differ from the task owner and must never receive unrelated task state.
- Test disabled-by-default behavior and rollback, file-backed shared DB and unsupported different-DB/in-memory paths. Run existing queue, IPC, question, cancellation, scheduled-task and restart regressions. Fixtures and reports contain no household content or live provider calls.

## Owner-only hold inspection

The existing experimental hold module now has an **unregistered, read-only** `inspect_owned_hold` helper. Trusted runtime code must construct `AccountSession`; the helper rechecks an active owner and the corresponding hold, queue claim, engine-stamped task, schema and checkpoint version together in the same SQLite transaction. It returns only an opaque unavailable result or a held status, current checkpoint status and the fixed next step `requires_authorized_reconciliation`. It returns no claim generation, prompt, result, account contents or evidence. Missing/inconsistent data or another actor does not disclose whether a hold exists. The caller must recheck identity and delivery audience when presenting any result.

Inspection does not authenticate an IPC caller, resolve an uncertain action, release a hold, perform a retry or authorize deletion. In particular, a cancelled checkpoint can still contain an unresolved effect. The durable actor-scoped deletion gate, complete cross-store deletion journal and safe hold/effect-reconciliation contract above remain unimplemented; installing holds in a live household remains blocked. The tests use disposable SQLite, existing stores and trusted synthetic sessions; they do not establish a production identity or delivery route.
