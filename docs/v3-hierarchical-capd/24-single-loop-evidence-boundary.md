# Single-loop evidence and effect-settlement boundary

Status: unresolved integration blocker for #214. The experimental engine is unregistered; its checkpoint transaction refuses to settle every tool action. This document records why simply accepting a source ID or a tool result is insufficient and what a production integration must establish.

## Existing evidence is not a universal action receipt

- V3 tactical results (`executor.py`) and V2 `TaskState.evidence_journal` carry a call ID, result and status inside task state. V3 associates each evidence entry with an immutable phase scope and checks affected paths and verification metadata in `outer._invariant_violations`. That association and its scope checks must be replaced before removing phases; an action ID or result alone does not create authorization or prove the requested effect.
- `exact_text_edit` returns hashes and a post-write read-back; Bash verification can independently observe an authorized scoped resource before and after execution. These are operation-specific outputs from trusted code. Neither is a general-purpose independently persisted actor/task/action receipt that the experimental checkpoint can verify from an arbitrary reference. A process can crash after the external operation or observation and before the task checkpoint is stored.
- `v2_source_evidence` belongs to `SourceAcquisition` and is committed alongside its own scheduled check-run lease, policy revision, page and coverage. Access to its content requires actor, run, time window, policy and current grant checks. It does not by itself bind a candidate task action, action arguments, mutation scope or independent effect verification; reading a row by evidence ID would bypass that access path.
- `v2_outbox` records task ID, audience, channel and delivery state. The scheduled delivery-status path additionally verifies task, occurrence and recipient. An outbox row is not a universal receipt for a particular candidate action or for verified downstream resource state, and provider delivery must remain distinct from recipient read. Delivery may be pending, failed or unconfirmed.
- Authenticated question-answer receipts are created in the question-resume flow, with question/respondent binding. They establish an answer to that question; they are not tool-effect receipts and do not resolve unknown mutation outcomes.

The experimental task-budget reservation persists an opaque ID and resource charges, not the tool ID, arguments, action authority, allowed effects, intended resource, grant/binding revisions or a trusted observation. No existing row can therefore be safely joined to that reservation to prove that the recorded effect belongs to the action. A generic `evidence_ref` string, an `exit_code`, a process-success flag, a model judgment or an unrelated provider record is never sufficient.

## Required contract before tool settlement

1. **Before dispatch**, atomically bind a unique task/action attempt to the authenticated actor, engine/schema, exact tool and normalized arguments (or collision-resistant canonical digest plus durable arguments), intended resource and permitted effect scope, and applicable authority/binding/grant revisions. The actor must be derived from authenticated task state. Validate schema, prerequisites and current permission and record an in-flight marker with the budget reservation in the same durable transition.
2. **At dispatch and observation**, reuse the tool's existing actor- and resource-scoped authorization and cancellation checks. A same-database commit cannot atomically include external file, browser or provider I/O; therefore a crash, timeout, revocation, cancellation or lost response after dispatch must remain uncertain until an operation-specific reconciliation establishes what happened. Do not automatically replay an uncertain mutation or delivery.
3. **For each operation type**, define what its trusted result proves and what independent read-back or provider receipt is necessary. Validate the expected resource identity, action correlation, value/version or nonce, completeness, freshness and actual outcome. Preserve pending, denied, partial, failed, conflicting and unknown evidence distinctly. A successfully dispatched command or enqueued message does not prove the requested outcome.
4. **At settlement**, use the same database transaction to re-read the running owner-scoped task, current version, matching in-flight action and budget; enforce relevant current local grant/binding/authority revisions and cancellation state where those records share the transaction. Persist the verified, actor-visible action-bound observation and budget settlement before clearing the marker. If evidence or authority lives in another store, define its immutable receipt, access/revocation and fencing protocol explicitly; do not assume two database commits or an external service are atomic. If any condition is unavailable, retain the marker and return a truthful blocker.
5. **Before final response or next provider call**, recheck access to the exact source, its coverage and freshness, and action authority. Neither Jev's relevance/probability nor System Two's text can grant access, override a verification failure or turn incomplete evidence into success. Enforce channel/audience privacy independently of task ownership.
6. **After restart or cancellation**, expose only actor-authorized minimal reconciliation state. Reconcile in-flight effects without repeating them, preserve unknowns and user-visible cancellation, and protect the row against stale legacy writers. A read-only cancelled-row inspection exists in the prototype; a safe settlement/reconciliation path does not.

## Minimum disposable tests

Use actual task/checkpoint and relevant same-database authority/receipt stores with synthetic actors, actions, provider responses and resource identifiers. Cover forged and unrelated evidence IDs; another actor, task, action or resource; old grant/binding revision; revoked scope at each boundary; change in arguments or expected effect; partial/missing/conflicting read-back; fake success or successful command without effect; cancelled or failed provider result; stale concurrent writer; crash before dispatch, after external effect and before settlement; duplicate execution; pending/failed/unconfirmed outbox receipts; and provider delivery versus recipient read. Independently inspect the synthetic effect and count dispatches. Assert that no withheld or failed state clears the in-flight marker or yields terminal success.

Design the least general operation-specific path that meets this contract; do not create a new user-facing script registry or make scheduled source-acquisition evidence impersonate conversational actions. Wiring real effectful tools, operational question continuation and scheduled delivery remains #214 work. Compare complete trajectories using #212 and do not change the default engine until #215 passes.
