# First Codex subscription clock comparison

**Fairness issue found after the runs:** the synthetic V3 `native.respond` tool
was described as read-only and lacked the production tool's `user_response`
side-effect metadata. V3 planning and completion checks inspect these fields,
so the results below are valid observations of that fixture but cannot isolate
the V3 architecture's behavior. A corrected V3 fixture and a fresh run are
needed before treating the comparison as fair. Do not discard these results.

On 2026-11-11, the actual V3 and experimental simple-loop processors each ran
one synthetic fixed-clock task through the same ChatGPT-signed-in Codex CLI
(`codex-cli 0.156.1`, requested model `gpt-6-luna`). The CLI preflight reported
ChatGPT sign-in and the inference subprocess removed inherited API-key and
provider-override environment variables. No direct OpenAI API key was used.
V3 used the household's configured TypeSafe Jev key solely for the synthetic
clock task; four Jev transport attempts were observed. The provider/model
account entitlement and subscription billing mode at every instant cannot be
independently attested by the harness.

Both arms received independent fresh copies of the same synthetic instant
`2026-04-12T14:00:00+00:00` and `America/Mexico_City` timezone, a read-only
clock source, the same model and an 80-second cooperative test deadline.
The independent oracle checked that the source was read and the returned
structured local time/date matched the separate answer key. The tool was not
connected to a household clock, account, email or prescription. The test
operated at processor/fixture level, not the desktop/daemon conversation path;
user-facing delivery was unassessed. Model prompts and processor design differ
between arms, and source attribution is by bearer capability, not process ID.

**Subsequent harness review:** these V3 observations used a synthetic
`native.respond` descriptor generated by the generic replay fixture. It marked
the tool read-only and omitted the real product descriptor's `user_response`
metadata and exact schema. The V3 compatibility check does special-case
`native.respond` by ID, so the mismatch is not proof of the failure's cause;
it can nevertheless affect what V3 sees during planning and how response
evidence is represented. The clock harness now uses the real product response
descriptor and local payload builder without sending any message. Earlier V3
timings and failures describe the **old harness**, so repeat the V3 test with
the corrected harness before drawing a conclusion about the architecture.

A separately labeled additional simple-loop diagnostic took 9.54 s, made one
Codex call and no tool calls, and also entered `waiting_user`. Its returned
question said it could not access the synthetic `index` source and asked for
its contents or for `native.fixture_read` to be enabled. The candidate question
was not delivered to a user (`question_delivery_not_integrated`). This is a
clue about tool visibility or inference instructions, not proof of its cause.

The original aggregate output retained call counts and outcome checks but not
individual V3 trajectories, actual response text, token totals, provider
billing, or the exact prepared question from the first candidate attempt. The
subsequent diagnostic question was captured separately; it does not replace
or erase the first result. Available prompt token figures were estimated, not
provider-reported. No general success rate, cost saving, expected latency, or
architecture superiority can be inferred from these few runs. Unknown or
failed observations must not be counted as zero work or successful completion.

The result does show an actual failure for each loop on this first constrained
clock task under the current test integration: V3 read the clock but did not
produce a verified answer before the deadline; the candidate asked for a tool
it was expected to choose rather than reading it. Investigate the integration
and preserve both results before any changed-prompt rerun. Do not treat a mock
fixture pass as proof that the live path has been fixed.

## Exploratory candidate rerun after host-tool prompt correction

The candidate chooser was changed to describe the actual authorized host tool
and clarify that Alphonse executes a returned tool request; Codex itself is not
expected to have that tool. The prompt change supplied no answer and did not
change the deterministic authorization or read-only guards. This was a
post-observation exploratory correction, not a pre-registered held-out result.

One subsequent subscription-backed candidate attempt completed in **16.59 s**,
with two Codex calls and one clock read. The independent source/answer oracle
passed. The two visible input estimates were 577 and 624 tokens; output
estimates were 20 and 30 tokens, respectively, from the uncalibrated UTF-8
bytes/4 method. These are not provider-reported token usage or charges, and
exclude unobserved framing and reasoning. The categorical trace was one
`native.fixture_read` request followed by an answer. Delivery was unassessed.
This result suggests that clarifying the host/tool boundary helped on this one
case, but does not prove the cause or establish a reliability rate. Retain the
two earlier failed candidate runs and the original V3 result above.

## Additional V3 diagnostic with categorical trace

A further V3 attempt, without changing its decision prompts, used the same
subscription-backed provider, model, synthetic clock and 80-second test limit.
It was cancelled after **80.51 s**, with no verified answer. Eight Codex calls,
three instrumented tool invocations and four Jev transport attempts were
recorded. The clock oracle observed the correct source but did not observe a
verified answer. The categorical decision trace recorded task understanding,
phase planning, a clock-read decision, a `native.respond` decision, another
clock-read decision, another phase plan and another `native.respond` decision;
the final model call did not yield a traceable decision before cancellation.
A decision to invoke a tool is not itself proof that tool was dispatched or a
message delivered. The revised instrumentation counts `native.respond` calls
as well as reads; the earlier V3 receipt counted only clock reads, so raw tool
counts across those revisions are not directly comparable.

Using the same uncalibrated UTF-8-bytes/4 text estimator as the candidate
rerun, this V3 diagnostic's eight observed input prompts total approximately
**50,649 estimated tokens**. The corrected candidate run's two observed input
prompts totaled approximately **1,201 estimated tokens**. These values cover
visible text only, not provider framing or hidden reasoning, and are not actual
provider usage, subscription charges or a precise cost ratio. The sample is one
V3 diagnostic versus one post-fix candidate diagnostic; retain all failures,
and do not infer a population reliability rate or a controlled architectural
advantage from this small, post-observation sequence. The difference does
identify the prompt and repeated-call overhead worth investigating next.

## Second candidate run with the corrected host-tool prompt

A second fresh subscription-backed candidate attempt with the same corrected
host-tool prompt did **not** verify the task: after 7.53 s and one Codex call it
attempted an answer without a clock read, and the candidate returned `blocked`.
The independent source/answer oracle failed; delivery was unassessed. Visible
input and output estimates were 577 and 31 tokens using uncalibrated UTF-8
bytes/4; they are not provider usage or charges. The categorical trace recorded
an answer decision and no tool request. The runtime retained no answer text in
this receipt, so the content and the exact internal blocking reason cannot be
inferred from this output.

The corrected candidate therefore has one verified success and one failure in
this tiny post-fix sample. Both earlier pre-fix failures remain recorded above.
This is insufficient to claim dependable performance or a general improvement.

## Matched rerun after V3 response-tool correction

A fresh exploratory pair was run after the V3 fixture installed the actual
product `native.respond` definition and both arms received the same synthetic
source description. The simple-loop prompt was consequently a new version
relative to the earlier candidate outcomes; prior runs remain recorded above.

- Simple loop: completed in **14.67 s**, with 2 Codex calls and 1 tool call.
  The independent source and answer oracle passed. Estimated visible input and
  output were 1,176 and 50 tokens respectively; no provider usage was supplied.
- V3: reached the **80.41 s** deadline with 7 Codex calls, 3 instrumented tool
  calls and 5 Jev attempts. The source/answer oracle saw the correct prepared
  answer, but the processor's terminal status was `cancelled`, so this was not
  a verified completed task. No real user delivery was observed. Visible input
  was estimated at 36,539 tokens; output total was unknown because at least
  one call did not supply observable output. These are not provider token counts.

The V3 categorical trace contained clock-read and response decisions, including
repeated planning and another clock-read decision, before cancellation. A
prepared correct response is not proof the user received it. The two arms used
separate fresh synthetic fixtures and the same Codex subscription and requested
model, but their internal prompts, control flow, output bounds and Jev usage
differ. This remains one exploratory matched pair, not a general reliability
rate or a full desktop end-to-end test.
