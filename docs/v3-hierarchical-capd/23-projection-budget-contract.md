# Bounded evidence and task-budget foundation contracts

Status: standalone foundations for #210 and #213. These modules do not change the current runtime, provide a security boundary by themselves, or qualify the single-loop candidate for household use. Integration and end-to-end tests belong to #214; qualification belongs to #215.

## Decision evidence projection

`core/intelligence/v3/evidence_projection.py` exposes `project_evidence(sources, actor, budget, authorize, load)`. Each `EvidenceSource` names one atomic visibility unit and its kind. The caller supplies actor-scoped `authorize(actor, source_id)` and `load(actor, source_id)` functions backed by the real access and source services. A goal must be present; goals, constraints, effects and current results are mandatory when supplied. Additional sources can be marked mandatory.

The projection loads only authorized sources, rechecks access around loading and before return, and assembles whole records under a conservative UTF-8-byte budget. Required denial, failure, clipping or budget overflow fails closed. Optional denials and unavailable results are withheld; provider-visible coverage includes counts but not withheld IDs. Authorized over-budget or clipped IDs may be included in coverage for expansion. Coverage consumes the same budget. Coverage that cannot fit or stabilize fails closed. The manifest contains source IDs and coverage, not source content. It does not establish absence or success.

For targeted expansion, call the same function with the requested source marked required and reauthorize it; never trust an earlier projection as an access grant. Preserve underlying evidence in the existing durable stores. The caller must inventory all applicable goal, constraints, effect receipts, pending/uncertain effects and required observations; absent inventory is not detected by this module. Before dispatch, fence the actor's current authorization, cancellation and source versions, including revocation or changes after projection. Account for prompt framing, tool schemas and provider encoding outside the projection's budget. Decide how to handle incomplete coverage without claiming success. The loader must return an indivisible source with no mixed audiences, credentials or unauthorized content. The repeated callback checks cannot themselves eliminate races with the provider call.

## Durable task budget

`core/intelligence/v3/task_budget.py` provides `BudgetLimits`, `TaskBudget` and an optional file-backed `SQLiteTaskBudgetStore`. Limits are immutable per snapshot and cover tool actions, model calls, input/output token charges and elapsed wall time, with a protected final-response reserve. Each model retry or tool dispatch requires its own reservation ID. The store uses revision-based compare-and-swap; only one transition is saved per revision, and a conflict requires reload.

Before dispatch, call `store.reserve(...)` with the current revision and persist the reservation; dispatch only after it returns successfully. Settlement is a separate single transition that must also be CAS-persisted. Restart leaves pending reservations charged. Unknown provider token usage remains explicitly unknown and blocks subsequent model calls, including final-response inference, until authoritative reconciliation. A no-model fallback must be available when no safe final model call can be made. Release a reservation only on independently established proof that it was never dispatched; never infer that from timeout or crash.

The store's `reserve` also persists a valid observed timestamp when it rejects a request for budget exhaustion. This prevents a later clock rollback from reopening an already observed time window. Direct callers of `TaskBudget.reserve` must CAS-persist every changed revision, including when `BudgetExhausted` is raised, before handling that result. Clock readings are injected UTC wall-clock milliseconds; elapsed time includes waiting and downtime. A wall clock is not a trusted monotonic time source. The integration must supply an appropriate time policy, reject backwards observations, and document clock-adjustment behavior.

Token reservations are upper-bound estimates only if the integration actually constructs them that way. Provider-side output limits and safe accounting for the complete request, tool schemas, provider retries and unavailable usage are mandatory for a hard cap. The ledger records a reported overrun but cannot undo already spent tokens. The caller must persist a reservation before each actual provider attempt, including hidden SDK retries, or disable those retries. An in-memory object alone cannot prevent concurrent spending; use the CAS store or equivalent durable transaction.

Budget accounting never grants permission, verifies an external effect, controls cancellation, or makes an uncertain mutation safe to repeat. Integration must retain a durable action/authority snapshot and uncertain-effect state, recheck cancellation and current actor-scoped access before and after I/O, and reconcile uncertain writes or deliveries before retrying. The standalone budget store and task/effect checkpoints are not one atomic transaction: #214 must design and test their crash-consistent coordination and must not infer success from an accounting record.

## Verification boundary

The foundation tests use disposable data, an injected clock and synthetic authorization/loaders. They verify local boundedness, explicit omissions, fail-closed required evidence, revocation during loading, independent call accounting, CAS contention, unknown usage, restart and clock rollback. These tests do not establish provider-side enforcement, production authorization, an atomic cross-store checkpoint or live model behavior.

## Experimental checkpoint transaction

`single_loop_checkpoint.py` demonstrates a narrower integration against the existing `SQLiteQuestionStore` task-checkpoint row. An explicitly stamped `single_loop_experimental` task with schema 1 can atomically persist the candidate's in-flight marker and budget reservation, and later persist a settled model reservation. Tool settlement remains blocked until actor/action-bound durable evidence validation exists. It preserves unrelated task fields and checks the actor, row status, task and engine stamps, schema and expected row version inside an immediate SQLite transaction. Time observations made by budget rejections are committed before the rejection returns. Unsupported snapshots, stale versions and cancelled rows fail closed.

The adapter does not create or register an engine, alter a production schema, authorize or execute a tool, verify a response/effect or deliver a question. A crash before evidence-reference settlement leaves the action in flight; failed, timed-out or cancelled tool attempts remain in flight for future explicit reconciliation. A reference supplied by a caller is not proof that its target exists, is visible to the actor, or verifies an effect; tool settlement is rejected even when a reference is supplied. The tests exercise the existing SQLite task table only in disposable databases; they do not establish household authorization or effect correctness.

**Do not enable the candidate based on this transaction.** The two `SQLiteQuestionStore` replacement paths now reject overwriting an experimental-engine row inside their SQL statements, including a stale writer or a delegated-child ID collision; legacy nonexperimental collision behavior remains unchanged. The generic terminal-update API refuses done/failed for experimental rows, while cancellation remains available and retains in-flight state. The adapter can inspect a cancelled owner-scoped row for an in-flight reservation without exposing source content, but cannot reconcile or resume it. Other task checkpoint writers, external database access, task deletion, authorization and lifecycle behavior have not been qualified as a complete production concurrency contract. No transaction here spans external I/O, independent source/effect stores, cancellation or grant changes; real action dispatch must enforce and, where required, atomically fence those boundaries. Production integration must establish engine stamping and lifecycle routing, safe concurrent ownership, real evidence validation and reconciliation, question/schedule behavior, and migration/rollback before activation.

The unregistered `single_loop_atomic_step.py` passes one synthetic chooser decision through the task-row transaction. It reserves before the call, settles afterward, and refuses all tool dispatch, answer delivery and completion. It rechecks the durable row immediately before model dispatch, but SQLite cannot atomically fence an external provider request with subsequent cancellation or authorization changes. The real provider boundary and live actor-scoped authority remain blockers.
